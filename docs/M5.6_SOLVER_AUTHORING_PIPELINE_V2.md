# M5.6B — DIRECTIONAL GEOMETRY METRICS

The current analyzer's broad `reachablePixels()` exposure concept is not enough for Core V2.

Add ruleset-aware geometry analysis.

For `legacyV1`:
- preserve current behavior

For `coreV2`:
derive metrics from the actual directional/ray helpers used by gameplay.

Recommended Core V2 metrics:

```ts
directionalGeometry: {
  initiallyExposed: number;
  buried: number;
  maxLayerDepth: number;
  averageLayerDepth: number;
  singleSideExposed: number;
  multiSideExposed: number;
}
```

Definitions should be deterministic and documented.

Useful concepts:

- a pixel is "initially exposed" if at least one valid inward attack ray reaches it as the first occupied target
- "buried" means at least one blocking layer must be cleared before it can become first-visible
- layer depth = minimum blocking depth from any valid attack direction
- single-side exposed = currently available from exactly one perimeter side/directional line family
- multi-side exposed = available from more than one

Do not invent visual-only geometry approximations if engine helpers can be reused.

# M5.6D — WITNESS DECISION / CHOICE METRICS

Current tooling mainly classifies first moves.

M5.6 should also analyze meaningful decision states along a winning witness.

At each settled player-decision state:

1. enumerate legal player actions using runtime `legalActions`
2. count available actions
3. where practical, determine which candidate actions still have a winning continuation
4. classify the decision state

Recommended output:

```ts
choiceMetrics: {
  totalDecisionStates: number;
  forcedStates: number;
  multiOptionStates: number;
  statesWithMultipleWinningOptions: number;
  statesWithTrapOptions: number;
}
```

Definitions:

- forced state: exactly 1 legal accepted player action
- multi-option state: 2+ legal accepted actions
- multiple-winning-options: 2+ actions with winning continuation
- trap option: at least one legal action leads to an unsolvable/loss continuation while another still wins

Avoid exponential duplicate work if the solver can expose/reuse visited subtree information.

If exact trap analysis is too expensive for every decision state, provide a bounded deterministic implementation and clearly report limitations.

# M5.6E — DETERMINISTIC ANTI-SPAM POLICY

Add a deterministic naive-policy evaluator.

Purpose:

Not to "prove difficulty", but to detect levels where blind tunnel spam trivially wins.

Implement at least one policy:

## Policy A — Round-Robin Tunnel Spam

Concept:

- cycle tunnels `0 → 1 → 2 → 3 → ...`
- if selected tunnel action is illegal, advance to the next legal tunnel
- when no tunnel launch is legal, use a deterministic Holding fallback if one exists
- never use randomness
- bounded by a step cap
- uses the real runtime engine

Recommended output:

```ts
antiSpam: {
  policy: 'round-robin';
  outcome: 'won' | 'lost' | 'deadlocked' | 'step-cap';
  steps: number;
  peakHolding: number;
  maxActive: number;
  holdingEntries: number;
  manualRelaunches: number;
}
```

Hard/Super Hard quality warning:

If the naive policy wins easily, emit a design warning.

Do NOT convert that warning into an automatic hard failure yet.

Do NOT add random-policy simulations.

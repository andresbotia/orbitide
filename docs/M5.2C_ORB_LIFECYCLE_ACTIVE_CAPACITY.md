# Locked Product Rules

## 1. One launch = one perimeter pass

For Core V2:

A tunnel charge or held charge receives exactly one full perimeter circuit per launch/relaunch.

During that pass:
- directional targeting from M5.2B applies
- each successful shot spends exactly 1 capacity
- same attack-line bin cannot fire twice for that charge during the pass

At the end of the pass:

### If remaining capacity == 0
- charge is consumed
- active slot is freed

### If remaining capacity > 0
- charge goes to Holding
- remaining capacity is preserved
- active slot is freed

Do not allow a charge to circulate indefinitely.

---

# 2. Holding is post-pass parking

Holding is where a charge goes after completing its full pass with remaining capacity.

It is NOT an overflow queue for exceeding active capacity.

If there is no active slot available:
- a new tunnel charge cannot launch
- a held charge cannot relaunch

Do not automatically move newly tapped tunnel charges into Holding merely because Active is full.

---

# 3. Manual held relaunch

A held charge can be manually tapped/relaunched whenever:

- an Active slot is available
- the action is otherwise structurally legal

IMPORTANT CHANGE FOR CORE V2:

> A held charge does NOT need to have a currently visible/directionally hittable target in order to relaunch.

The player may intentionally relaunch a held orb even when it currently has no target.

Reason:
- another active orb may expose a target during this pass
- the player is choosing to spend an Active slot strategically
- this is required for harder juggling gameplay

On successful relaunch:
- the Holding slot is freed immediately
- the same charge identity is preserved
- remaining capacity is preserved
- the charge begins a fresh one-pass Core V2 circuit

Legacy V1 behavior must remain unchanged.

---

# 4. Tunnel launch with no current target

For Core V2, a tunnel charge may launch even if it has no currently hittable directional target, provided:

- an Active slot is available
- the action does not violate current Holding/deadlock constraints

It may travel its full pass with zero hits and then enter Holding with its full remaining capacity.

Do not require an immediate directional target as a launch prerequisite.

This is intentional.

Current project behavior uses a fixed constant of 5 in several places.

Core V2 requires:

```ts
activeCount
activeCapacity
```

Default Core V2 active capacity:

```text
5
```

Future item support will temporarily allow:

```text
6
```

Do NOT implement the item.

Do NOT expose purchasing/economy.

The engine and session architecture simply must stop assuming that the capacity can only ever be 5.

---

# 6. Engine admission must enforce Active capacity

For Core V2, Active capacity is a real gameplay constraint.

If:

```text
activeCount >= activeCapacity
```

then:

- tunnel launch is denied
- Holding relaunch is denied
- no engine mutation occurs
- no charge is removed from its source
- no queue advances
- no Holding slot is freed

This must be enforced by engine truth, not only presentation/session state.

Do not rely solely on `useGameSession`'s visible-flight guard.

Legacy V1 behavior should remain compatible with existing tests unless a minimal shared refactor is safe.

---

# 7. Variable capacity architecture

Preferred shape:

```ts
GameState.activeCapacity: number
```

and/or an architecture-consistent equivalent.

Core V2 default:
`5`

Existing UI/session selectors should be able to read:

```ts
activeCount
activeCapacity
```

Do not hardcode `5` at consumer call sites introduced/modified in this phase.

If existing legacy state needs a default, preserve legacy behavior.

---

# 8. Concurrency remains real

Do not serialize charges.

Up to `activeCapacity` active passes may coexist.

For default Core V2:
- 0 through 5 active is legal
- sixth launch is denied until a slot frees

Later, if activeCapacity becomes 6:
- six must be possible without architecture changes

Do not implement capacity 6 UI or item behavior now.

---

# 9. Slot release timing

An Active slot is released only when the corresponding active pass resolves to:

- `consumed`
or
- `holding`

Do not free the slot early merely because:
- the orb currently has no target
- the orb is between attack lines
- the orb has already fired once
- the orb is visually near the end of the path

Engine lifecycle remains authoritative.

---

- park it
- preserve id/color/remaining capacity

If Holding is full:
- preserve the existing engine's deterministic loss/admission model unless a Core V2-specific incompatibility is discovered

Do NOT increase Holding from 3 to 4 yet.

Do NOT redesign failure rules in this phase.

Report any issue that M5.2D must resolve.

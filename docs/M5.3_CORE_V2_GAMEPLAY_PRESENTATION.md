Gameplay presentation / UI / animation implementation.

Do not redesign engine mechanics.
Do not modify campaign content.

# Visual North Star

Pixel Arcadia should feel:

- bright
- lively
- premium
- arcade-like
- dimensional / 2.5D
- readable at a glance
- playful without feeling childish
- cleaner and less dark/sci-fi than the old gameplay screen

The target gameplay composition is:

- a large rounded-rectangle playfield
- a visible perimeter track around the board
- colorful numbered Pixel Pal orbs moving around that perimeter
- four compact feeder/tunnel lanes
- four Holding bays
- clear ACTIVE X/Y status
- crisp attack/projectile feedback
- strong hierarchy with the board as the main focus

Do not copy another game's artwork, characters, branding, exact UI, or assets.

We are borrowing only high-level interaction/readability lessons:
- slower readable perimeter movement
- visible feeder queues
- visible active count
- clear first-line attacks
- deliberate pacing

Pixel Arcadia must look original.

# Existing Engine Rules — DO NOT CHANGE

Core V2 already implements:

- ruleset: coreV2
- rounded-rectangle perimeter geometry
- directional inward targeting
- first occupied cell blocks the ray
- wrong-color blockers
- no same-line drill-through
- one shot opportunity per attack-line bin per pass
- deterministic concurrency
- one launch/relaunch = one complete perimeter pass
- remaining count after the pass goes to Holding
- activeCapacity default = 5
- future activeCapacity = 6 supported
- exactly 4 tunnels
- exactly 4 Holding slots
- exactly 3 visible queue entries per Core V2 tunnel
- deeper queue remains hidden
- manual held relaunch
- Core V2 no-target launch/relaunch is legal
- terminal deadlock logic is implemented
- Legacy V1 remains isolated

Do not rewrite any of these rules.

# 1. Replace Circular Gameplay Presentation

The old circular rail presentation is no longer the Core V2 visual model.

For Core V2:

- render a rounded-rectangle arena/perimeter
- use the existing engine rounded-perimeter geometry as the source of truth
- map normalized engine progress to the same rounded-rectangle path
- remove visual disagreement between engine targeting and presentation

Legacy V1 may continue using its existing presentation if necessary.

Do not force Legacy V1 through the new Core V2 presentation if doing so risks regressions.

---

# 2. Rounded-Rectangle Arena

The playfield should be a large rounded rectangle with enough interior space for dense pixel art.

Requirements:

- centered composition
- board is dominant
- perimeter rail visually distinct from the pixel grid
- smooth rounded corners
- enough exterior clearance for Pixel Pals to travel without covering the artwork
- rail should feel integrated into the cabinet/arcade environment
- avoid giant chrome machinery
- avoid excessive borders or decorative clutter

The board must remain legible for large/dense future levels.

Do not change board-size limits in this phase.

---

# 3. Pixel Pal — Core Orb Character

Use the approved **1B direction** as the design basis.

Pixel Pal should be:

- a rounded-square / soft cabinet-like arcade creature
- not a plain circle
- not an animal copied from another game
- not a mascot that replaces the Pixel Arcadia brand/logo
- compact enough to read while moving around the rail

Required visual features:

- colored outer shell/body representing gameplay color
- glossy dark face/visor
- simple expressive eyes
- large, high-contrast remaining-count number
- subtle side pods / small limb-like forms
- premium 2.5D depth
- soft highlight/shadow
- readable at small sizes

The SAME character species/body is used for all gameplay colors.

Do not create unrelated character variants per color.

---

# 4. Pixel Pal Number Readability

The remaining count is gameplay-critical.

It must be readable in all states:

- tunnel CURRENT position
- tunnel NEXT / NEXT+1 previews
- active perimeter movement
- Holding
- firing moment

The number should:

- be centered on a clear front-facing plate or torso area
- use high contrast
- not disappear against bright shell colors
- update immediately and visibly after each successful shot

Do not rely only on tiny text labels outside the character.

---

# 5. Pixel Pal Animation States

Implement clear, lightweight animation states.

At minimum:

## Idle / queue
- subtle breathing / hover / blink
- restrained, not distracting

## Launch anticipation
- brief squash/lean/wind-up
- clear departure from tunnel lane

## Perimeter travel
- smooth constant-speed movement
- subtle bob
- orientation follows perimeter travel
- slight banking/lean through rounded corners

## Target acquired / fire
- very brief anticipation
- face/eyes react subtly
- core/pod emits projectile
- small recoil

## Hit
- projectile impact flash
- affected board cell responds
- Pixel Pal number decrements

## Holding arrival
- character leaves perimeter and settles into a Holding bay
- do not teleport if an existing transition path can be used

## Held relaunch
- character leaves Holding and rejoins launcher/perimeter
- reuse the same Pixel Pal identity/color/count

## Consumed
- when remaining count reaches 0, use a compact satisfying exit/pop/dissolve
- do not send it to Holding

Animations should remain fast enough to keep the game responsive but slow enough to read.

---

# 6. Perimeter Speed

The old gameplay rail is too fast.

Core V2 visual target:

```text
FULL PERIMETER PASS ≈ 8.0 seconds
```

Use approximately:

```text
8000 ms
```

as the initial baseline.

Acceptable tuning range:

```text
7.5–9.0 seconds
```

unless existing animation infrastructure strongly favors a nearby value.

Requirements:

- define the timing centrally
- do not scatter magic `8000` constants
- engine simulation remains normalized/deterministic
- visual timing maps normalized pass progress to wall-clock animation
- do not change engine event ordering
- do not make Hard levels faster as a difficulty mechanic

This slower speed is intentional.

The player needs time to:
- track multiple active Pixel Pals
- see blockers
- anticipate hits
- decide whether to launch another queue
- manage Holding
- understand remaining counts

---

# 7. Launcher / Entry Point

Do not launch Pixel Pals magically from the board center.

Core V2 should visually use:

> one shared perimeter launcher entry point

Recommended position:

- bottom-center / lower perimeter area
- consistent with engine bottom-center start

The four feeder lanes merge visually toward this shared entry.

Requirements:

- tunnel selection determines which Pixel Pal feeds into the launcher
- character visibly travels/feeds toward perimeter entry
- no giant center cannon/hub
- launcher should feel compact and arcade-like

Do not change engine launch origin.

---

# 8. Four Feeder / Tunnel Lanes

Core V2 has exactly four tunnels.

Redesign their presentation as compact/open feeder lanes rather than large machine panels.

Each lane shows exactly:

```text
CURRENT
NEXT
NEXT+1
```

That means 3 visible Pixel Pals total.

Requirements:

- CURRENT is visually strongest/largest
- NEXT slightly smaller
- NEXT+1 slightly smaller/subdued
- queue direction is immediately obvious
- hidden queue remains hidden
- after launch, entries slide forward smoothly
- fourth hidden entry becomes visible as NEXT+1
- lane remains easy to tap
- four lanes fit cleanly without overwhelming the board

Do not render hidden queue items.

Do not change Legacy V1 magazine behavior unless required for shared-component safety.

---

# 9. Holding — Four Bays

Core V2 has exactly four Holding slots.

Redesign Holding as four compact parking bays.

Requirements:

- each held Pixel Pal remains clearly identifiable
- preserve color
- preserve count
- empty slots are visible
- occupied slots feel parked, not active
- tap target is generous
- relaunch animation clearly frees the bay

Visual pressure should increase naturally as Holding fills, but do not overdo warnings.

Capacity-aware behavior already exists:
- warning at capacity - 1
- full at capacity

Do not change the underlying Holding rules.

---

# 10. ACTIVE X/Y HUD

Add a clear but compact active-orb status:

```text
ACTIVE 3/5
```

Read from existing session/engine values:

- activeCount
- activeCapacity

Requirements:

- visible during gameplay
- not dominant over the board
- updates immediately
- supports future `6` without layout changes

Do not hardcode `/5` in the component.

---

# 11. Projectile / Attack Presentation

Pixel Pal attacks should feel crisp and readable.

Use:
- short energy projectile / beam / pulse
- color keyed to the Pixel Pal
- fast travel from Pixel Pal toward the targeted cell
- small impact bloom
- cell-specific response

Do not use:
- literal firearms
- giant explosions on every shot
- screen-filling particles

The user requested more visual feedback, but we do not want to overdo the UI.

Aim for:
- satisfying
- compact
- readable
- premium

---

# 12. Board Cell Feedback

A successful hit should visibly communicate what happened.

Ordinary clear:
- flash / pop / dissolve / pixel collapse

Frozen:
- crack/break ice layer

Shielded:
- shield shell pulse/break

Linked:
- existing linked visual language remains, improve only if needed for readability

Do not redesign special mechanics.

Presentation must follow engine events rather than inventing outcomes.

---

# 13. Brighter Pixel Arcadia Environment

The old screen leans too dark.

Shift Core V2 toward:

- rich navy / indigo base
- brighter blue/purple arcade accents
- luminous but controlled highlights
- colorful Pixel Pals
- lighter visual separation around board / controls
- stronger contrast between interactive and decorative elements

Avoid:
- pure black dominating the screen
- muddy dark grays everywhere
- excessive neon glow
- over-saturated rainbow noise

The artwork inside the board should remain the main color focal point.

# 19. Performance

Multiple Pixel Pals can be active simultaneously.

Default activeCapacity is 5.

Presentation must remain smooth with:
- 5 active Pixel Pals
- 4 feeder lanes
- 4 Holding characters
- dense boards
- simultaneous projectiles/impacts

Avoid:
- React state updates every animation frame
- unnecessary rerenders of the full board
- expensive blur layers stacked everywhere
- unbounded particles
- separate heavyweight canvases per character if avoidable

Use the project’s existing animation/rendering stack appropriately.

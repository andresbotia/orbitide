# Context

M5.2A added a pure rounded-rectangle geometry module:

- `src/game/geometry/roundedPerimeter.ts`
- path-distance progress
- clockwise traversal
- point-at-progress
- inward normal
- segment identity
- bottom-center progress = `0.5`

Current gameplay still uses legacy circular/global targeting.

M5.2B replaces the **target-selection rule** while preserving the rest of the engine architecture.

The goal is to eliminate the current spam-clear behavior caused by:

- global exterior flood-fill targetability
- immediate target acquisition
- multiple newly-exposed same-line pixels clearing instantly

# Locked Core V2 Rules For This Phase

## 1. Attack origin

Targeting must use the new rounded-rectangle perimeter geometry.

For a charge at pass progress `p`:

```text
geometryProgress = normalize(0.5 + p)
```

because Core V2 keeps bottom-center as the logical launch/insertion reference.

Attack origin:

```ts
geometry.pointAt(geometryProgress)
```

Attack direction:

```ts
geometry.inwardNormalAt(geometryProgress)
```

Do not use the current circular orbit point for targeting.

Presentation may temporarily remain circular until a later phase.

Engine truth should move first.

---

## 2. Directional ray rule

At a given attack-line encounter, cast inward from the orb's rounded-perimeter position.

The ray may interact only with the:

> **FIRST OCCUPIED BOARD CELL IT INTERSECTS**

Nothing behind that occupied cell is visible to this orb from this attack line.

This is true regardless of color.

---

## 3. Matching front cell

If the first occupied cell:

- is uncleared
- matches the orb color
- is otherwise eligible under existing modifier rules
- has not already been consumed for this attack line during this pass

then it may be shot.

Exactly one capacity is spent.

---

## 4. Wrong-color front cell

If the first occupied cell is a different color:

> it BLOCKS the ray.

Do not search behind it.

Do not skip it.

Do not hit a same-color cell behind it.

---

## 5. Empty cells

Empty / cleared cells do not block.

The ray continues inward until:

- it hits the first occupied cell, or
- exits the board with no target

---

## 6. No drill-through

This is a hard rule.

Example:

```text
RED orb ---> [RED A][RED B]
```

During one attack-line encounter:

1. RED A is first occupied.
2. RED A is hit/cleared.
3. RED B becomes exposed.
4. RED B may NOT be hit immediately from that same attack-line encounter.
5. The orb continues traveling.
6. RED B can only be hit from a later valid attack-line encounter.

Do not recompute the same line immediately after a hit and chain deeper.

---

## 7. One shot per attack-line bin per pass

Each logical attack line can fire at most once for a given charge during one perimeter pass.

This prevents frame-based duplicate hits and same-line drill-through.

Use deterministic attack-line bins.

### Straight edges

Recommended:

- top / bottom → one bin per board column
- left / right → one bin per board row

### Rounded corners

Use quantized ray/bin identity derived deterministically from the rounded-perimeter geometry and grid traversal.

The exact representation is up to implementation, but it must be:

- deterministic
- frame-rate independent
- stable across repeated simulation
- finite
- testable
- compatible with one-pass traversal

Do not use arbitrary presentation-frame sampling as the source of truth.

# Attack-Line Eligibility

The first occupied cell decides the ray outcome.

## Ordinary matching pixel

If matching:
- fire
- spend 1
- resolve existing clear behavior

## Ordinary wrong-color pixel

- blocks
- no shot
- no capacity spent

## Frozen / Shielded

Keep existing modifier semantics.

If the first occupied cell is matching and can legally receive the current layer hit:
- resolve exactly one layer/hit
- spend 1
- cell remains occupied if the modifier leaves it present

The same attack-line bin must not hit that cell again during the same pass.

If Frozen/Shielded is wrong-color or otherwise not eligible:
- it still blocks the ray

## Linked

Keep current Linked semantics.

If a Linked member is already primed:
- it remains occupied
- it blocks the ray
- do not shoot through it

If an unprimed matching Linked member is legally hittable:
- resolve existing prime/group-clear behavior
- spend capacity according to existing rules

Do not rewrite the Linked subsystem.

## Other modifiers

Do not invent new rules for:
- Armored
- Locked
- Bomb
- Wild
- Hidden

If they are currently presentation-only, treat them as ordinary occupied colored cells for this phase.

# Perimeter Progress

M5.2A uses:

- geometry progress 0 = top-center
- bottom-center = 0.5

Current logical pass progress begins at 0 from bottom insertion.

Therefore use:

```ts
geometryProgress =
  normalizePerimeterProgress(
    ROUNDED_PERIMETER_BOTTOM_CENTER_PROGRESS + passProgress
  );
```

or equivalent.

Do not reuse `pixelAngleFraction` as path progress.

# Candidate Search

The current `pickEncounter` behavior must change.

Current bad behavior:

- builds a globally reachable matching set
- sorts by angle
- frequently returns progress equal to the current position
- re-evaluates after a hit
- immediately chains through newly exposed pixels

New behavior:

1. Determine the next unused attack-line bin ahead on the remaining pass.
2. For that bin, cast inward.
3. Inspect first occupied cell.
4. If matching + eligible:
   - create one encounter candidate.
5. If blocked / wrong-color / no occupied cell:
   - that bin produces no shot.
6. Continue searching forward for the next unused bin.
7. Stop when:
   - a valid candidate is found, or
   - no attack-line bins remain in this pass.

The engine should not repeatedly poll the same bin.

# Concurrency

Keep the current epoch architecture.

Do NOT serialize active charges.

Do NOT reduce max active charges.

When two orbs compete:

1. Each produces a candidate event.
2. Existing global arbitration should continue to use deterministic ordering:
   - event time / progress
   - launch sequence
   - stable pixel-id tie break where needed
3. Winner resolves first.
4. Board mutates.
5. Other active charges re-query.
6. If a target disappeared, the losing charge:
   - spends no capacity
   - must not magically shoot through the newly exposed rear pixel from the same already-consumed attack-line bin
7. It continues to its next valid unused attack-line bin.

This last rule is critical.

---

# Same-Line Concurrency Rule

Example:

Two RED orbs reach the same line.

Front target = RED A.
Behind it = RED B.

Orb 1 wins arbitration and clears RED A.

Orb 2 must NOT immediately clear RED B from the same line/bin.

That line encounter is already consumed for Orb 2 once it reached that bin and lost the target race.

The orb must move on.

This preserves:

> one shot opportunity per line per pass

even under concurrency.

Implement/test this explicitly.

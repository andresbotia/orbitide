# Context

Pixel Arcadia is beginning **M5 — Core Gameplay V2**.

The existing gameplay engine uses a circular orbit/perimeter model. Real-device testing showed that the circular presentation wastes space and no longer matches the intended game.

Core V2 will use a:

> **ROUNDED-RECTANGLE PERIMETER**

Future phases will use this path for:

- character/orb movement
- launcher entry
- directional inward firing
- one-shot-per-attack-line targeting
- multi-orb concurrency
- Holding/relaunch behavior

This phase must create the deterministic geometry foundation required for those later systems.

The current pure engine architecture should remain intact.

---

# Locked Product Decisions Relevant to This Task

## Playfield

The gameplay board will eventually sit inside a rounded-rectangle perimeter.

The perimeter should:

- surround the board
- have straight top/bottom segments
- have straight left/right segments
- have smoothly rounded corners
- support deterministic clockwise traversal
- map normalized progress to position
- provide the inward-facing normal/vector at every position
- work for rectangular boards, not only square boards

The geometry must be defined independently from visual pixels or device screen coordinates where practical.

# Goal

Implement a small, pure, deterministic rounded-rectangle perimeter geometry module that can later replace circular orbit math.

The module should support at minimum:

1. normalized progress → perimeter point
2. normalized progress → inward unit normal
3. perimeter point → segment identity
4. perimeter total length
5. deterministic clockwise traversal
6. configurable board width/height
7. configurable corner radius
8. normalized progress wrapping

# Coordinate System

Use a deterministic 2D coordinate system.

Recommended convention:

- top-left = `(0, 0)`
- positive X → right
- positive Y → down

The rounded perimeter bounds should be defined by:

```ts
type RoundedPerimeterBounds = {
  x: number;
  y: number;
  width: number;
  height: number;
  radius: number;
};
```

Equivalent naming is acceptable if it matches project conventions.

Clamp corner radius safely.


Reject or normalize invalid values according to existing repo conventions.

The geometry must remain deterministic for:

- square boards
- wide rectangles
- tall rectangles
- radius 0
- maximum legal radius

# Traversal Direction

Use:

> **CLOCKWISE**

for the canonical positive-progress direction.

Progress should be normalized:

```text
0 <= progress < 1
```

Values outside that range should wrap deterministically.

Examples:

```text
1.0  -> same location as 0.0
1.25 -> same location as 0.25
-0.1 -> wraps near the end
```

Provide a helper such as:

```ts
normalizePerimeterProgress(progress: number): number
```

or reuse an existing safe normalization helper if appropriate.

# Perimeter Segments

The implementation should be able to identify which portion of the perimeter a progress value lies on.

Recommended segment identities:

```ts
type RoundedPerimeterSegment =
  | 'top'
  | 'topRight'
  | 'right'
  | 'bottomRight'
  | 'bottom'
  | 'bottomLeft'
  | 'left'
  | 'topLeft';
```

Equivalent enum/union naming is fine.

This will be useful later for:

- attack-line binning
- launcher placement
- animation orientation
- debugging

---

# Perimeter Length

Compute true rounded-rectangle perimeter length.

For bounds width `W`, height `H`, radius `R`:

Straight lengths:

```text
top/bottom = W - 2R
left/right = H - 2R
```

Combined corner arcs equal one full circle:

```text
2πR
```

Total:

```text
2(W - 2R)
+ 2(H - 2R)
+ 2πR
```

Handle radius 0 correctly.

Do not approximate the arc length with arbitrary constants.

---

# Position Along Perimeter

Implement a deterministic function conceptually equivalent to:

```ts
pointAtRoundedPerimeterProgress(
  bounds,
  progress
): { x: number; y: number }
```

The exact name is up to project convention.

Requirements:

- progress advances clockwise
- constant progress speed corresponds to constant path distance
- no speed jumps at corners
- position is continuous at every segment boundary
- rectangular boards work correctly

---

# Inward Normal

Implement a deterministic function conceptually equivalent to:

```ts
inwardNormalAtRoundedPerimeterProgress(
  bounds,
  progress
): { x: number; y: number }
```

The vector should be normalized.

Straight edges:

Top:

```text
(0, +1)
```

Right:

```text
(-1, 0)
```

Bottom:

```text
(0, -1)
```

Left:

```text
(+1, 0)
```

Rounded corners:

The inward vector should point from the perimeter point toward the corresponding corner-circle center / interior.

It must rotate smoothly through the corner.

This normal will become the attack direction in M5.2B.

Do not perform pixel intersection/raycasting yet.

# Performance

This math will eventually run frequently.

Keep it:

- pure
- allocation-light
- deterministic
- O(1) per query

Avoid:

- sampled path arrays
- iterative searching
- frame-dependent state
- React dependencies

Precomputing a compact geometry descriptor from bounds is acceptable if beneficial.

For example:

```ts
const geometry = createRoundedPerimeterGeometry(bounds);
geometry.pointAt(progress);
geometry.inwardNormalAt(progress);
```

Use whichever API produces the cleanest and fastest implementation.

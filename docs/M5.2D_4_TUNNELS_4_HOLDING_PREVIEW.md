# Locked Product Rules

## Core V2 tunnels

Core V2 standard:

```text
4 tunnels
```

Each tunnel contains a potentially deep authored queue.

The player sees only:

```text
CURRENT
NEXT
NEXT+1
```

That means **3 total visible entries**, including the loaded/current orb.

Example authored queue:

```text
WHITE 8
BLUE 10
RED 6
ORANGE 11
PURPLE 7
GREEN 12
...
```

Visible:

```text
WHITE 8 | BLUE 10 | RED 6
```

After WHITE launches:

```text
BLUE 10 | RED 6 | ORANGE 11
```

The rest stays hidden.

Do not expose the entire queue.

# Tunnel preview depth

Current audit found `TunnelBar.MAX_PREVIEWS = 3` **plus the loaded front**, meaning 4 entries are effectively shown.

Core V2 product rule is:

> 3 total visible entries.

That means:

- loaded/current
- next
- next+1

Only 2 preview entries behind the front.

Implement this cleanly.

Prefer a constant whose meaning is unambiguous, e.g.:

```ts
VISIBLE_TUNNEL_ENTRIES = 3
```

or:

```ts
MAX_UPCOMING_PREVIEWS = 2
```

Avoid a misleading constant where "3 previews" actually means 4 visible entries.

Legacy V1 may use the same 3-total-visible presentation if it does not change gameplay information required by existing product behavior.

If changing V1 preview information is considered a migration risk, make the preview depth ruleset-aware and report why.

# Queue behavior

The underlying full queue remains unchanged.

Launching the front charge should:

1. remove only the current/front entry
2. shift remaining queue forward
3. reveal the next hidden entry into the visible 3-entry window

Example:

Before:

```text
A | B | C | D | E
visible: A B C
```

Launch A:

```text
B | C | D | E
visible: B C D
```

No authored queue order changes.

No randomization.

No truncation.
